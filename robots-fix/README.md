# Fix: "Blocked due to other 4xx issue" (validation failed 2026-09-14)

## What actually failed

Search Console's validation failed on **one** URL:

```
https://www.oligopolypeptides.com/?wc-ajax=ppc-create-setup-token
→ HTTP 400  {"success":false,"data":{"message":"Could not validate nonce."}}
   X-Robots-Tag: noindex
```

That 400 is correct behaviour. It is the WooCommerce PayPal Payments setup-token
endpoint, and it rejects any request without a valid nonce — which is exactly what an
unauthenticated crawler sends. The endpoint is not a page, has no content, and must
keep returning 400. Nothing about it should be "fixed" server-side.

The problem is that Googlebot found the URL at all. WooCommerce prints its AJAX base
URL into the inline JS of every storefront page (`?wc-ajax=%%endpoint%%`), Google
follows those strings, and every 4xx answer lands in this report.

So the fix is to stop crawlers from requesting `wc-ajax` URLs — not to change what
those URLs return.

## The change

One line added to `robots.txt`:

```
Disallow: /*?wc-ajax=
```

Full intended file: [`robots.txt.proposed`](robots.txt.proposed) (the only difference
from the live file is that single line, inserted next to the existing
`Disallow: /*?add-to-cart=`).

`robots.txt` is read by crawlers only. Browsers, WooCommerce and PayPal's servers never
consult it, so checkout, the PayPal buttons and the nonce check are untouched.

## How to apply it

The site serves a *virtual* robots.txt generated by WordPress (Rank Math SEO is the
active SEO plugin, alongside the in-house "OligoPoly SEO Remediation" plugin), so there
is no file to edit at the document root. Pick one route:

1. **Rank Math** (fastest) — *WP Admin → Rank Math SEO → General Settings → Edit
   robots.txt*, add `Disallow: /*?wc-ajax=` under `Disallow: /*?add-to-cart=`, save.
2. **WPCode Lite or Code Snippets** (both already active) — add a new PHP snippet set to
   run everywhere, pasting the `add_filter( 'robots_txt', … )` block from
   [`oligopoly-robots-wc-ajax.php`](oligopoly-robots-wc-ajax.php) (everything below the
   `defined( 'ABSPATH' )` line).
3. **As code** — drop [`oligopoly-robots-wc-ajax.php`](oligopoly-robots-wc-ajax.php) into
   `wp-content/mu-plugins/`, or fold the same filter into the existing OligoPoly SEO
   Remediation plugin, which already filters robots output.

The filter is idempotent and runs at `PHP_INT_MAX - 10`, so it lands after Rank Math and
after the remediation plugin, and it will not duplicate the rule if a second route is
used later.

## Verification

Two harnesses, both read-only:

```bash
python3 robots-fix/check-robots-coverage.py robots-fix/robots.txt.proposed  # rule semantics
bash    robots-fix/verify.sh                                                # live site
```

`check-robots-coverage.py` implements Google's matching rules (`*`, `$`, longest match
wins, Allow breaks ties) and was run against the proposed file before deployment:

* blocks `?wc-ajax=ppc-create-setup-token`, `?wc-ajax=%%endpoint%%`,
  `get_refreshed_fragments`, `add_to_cart`, `checkout`
* keeps `/wp-admin/admin-ajax.php`, `/wp-json/oligopoly/v1/coa` and every content URL
  crawlable
* **224 / 224 sitemap URLs stay crawlable — zero collateral**

`verify.sh` checks the live site: the rule is present exactly once, the sitemap
directive and the `admin-ajax.php` Allow survived, the setup-token endpoint still
answers `400 Could not validate nonce` (proof the nonce check was not weakened), cart
fragments still answer 200, and the storefront, a live product page with its PayPal
assets, and `/checkout/` all respond as before.

Baseline from before the change:
[`../evidence/wc-ajax-4xx-verification-2026-09-17.txt`](../evidence/wc-ajax-4xx-verification-2026-09-17.txt).

## After it is live

1. Run `bash robots-fix/verify.sh` — it must end in `RESULT: PASS`.
2. Place a test order (or at least open the PayPal button on a product page) before the
   change is considered signed off. robots.txt cannot break it, but the checkout path is
   worth a human click either way.
3. In Search Console, open *Page indexing → Blocked due to other 4xx issue* and start a
   **new** validation. The 2026-07-07 validation that failed on 2026-09-14 cannot be
   resumed.
4. Expect `?wc-ajax=` URLs to move out of this report and into "Blocked by robots.txt",
   which is the correct resting place for an internal endpoint.

## The other four example URLs — no action

| URL | Live now | Why it needs nothing |
|---|---|---|
| `/wp-admin/admin-ajax.php` | 400 | Correct without an `action` parameter. It is `Allow`ed on purpose so Googlebot can fetch AJAX-driven resources while rendering; blocking it to tidy this report would cost more than it saves. |
| `/wp-content/*` | 404 | A literal wildcard string, not a page. It is not linked and not in robots.txt; it will age out of the report. |
| `/wp-json/oligopoly/v1/coa` | 200 + `X-Robots-Tag: noindex` | Already fixed. Search Console's record is stale. |
| `/?wc-ajax=%%endpoint%%` | 200 (301 from the non-www host) | Already fixed. Stale record; the new rule also stops it being crawled. |

The wider indexing picture — 1,028 non-indexed vs 289 indexed on 2026-09-13 — is not
driven by these five URLs. See [`../FINDINGS.md`](../FINDINGS.md) for that work.
